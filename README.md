# Облако TUTOR DESK Web v5 (Supabase)

Без настроенного проекта приложение остаётся локальным. Для облачных функций требуется собственный Supabase-проект. В браузер можно вставлять только Project URL и publishable/anon key. Никогда не используйте `service_role` или secret key.

## Подключение
1. Создайте проект в Supabase.
2. Откройте SQL Editor и выполните `schema.sql` целиком. Скрипт создаёт таблицу рабочего состояния с номером версии, приватное хранилище файлов `tutor-materials`, политики доступа и таблицу статуса подписки.
3. В Authentication → URL Configuration настройте Site URL и Redirect URLs для своего локального адреса или HTTPS-домена.
4. Запустите приложение через `Запустить-на-Mac.command`, нажмите «Облако» и укажите URL и publishable/anon key.
5. Создайте аккаунт или войдите. После подключения локальные изменения отправляются с небольшой задержкой. Ручные кнопки остаются доступны.

## Автосинхронизация и конфликты
- Изменения в локальной базе автоматически отправляются в облако примерно через 1,8 секунды после сохранения, если пользователь вошёл и подключён Supabase.
- Приложение хранит отметку последней синхронизированной версии и при обнаружении изменения с другого устройства останавливает автозапись, чтобы не перезаписать данные молча.
- В случае конфликта откройте облако и осознанно выберите загрузку либо ручную перезапись после резервного копирования.
- Для полноценного коммерческого запуска требуется дополнительное серверное compare-and-swap/атомарное сохранение и тесты гонок синхронизации. Текущая проверка конфликта снижает риск, но не является абсолютной защитой от одновременных записей в одну миллисекунду.

## Файлы библиотеки
- Нажмите «Синхронизировать файлы» или «Сохранить в облако». Файлы загружаются в приватный bucket, ограниченный UUID пользователя.
- Размер одного файла в настройке bucket ограничен 50 MiB. Учитывайте квоты и стоимость хранения Supabase.
- Файлы загружаются и скачиваются только после входа. При восстановлении метаданные и бинарные файлы сохраняются отдельно.

## Подписки
Таблица `tutor_subscriptions` хранит статус плана и доступна пользователю только для чтения. Для каждого нового аккаунта создаётся запись базового плана. **Реальные платежи не подключены:** перед продажей подписки нужно выбрать платёжного провайдера, реализовать проверяемый серверный webhook/Edge Function, управление продлением/отменой и проверку прав на сервере. Нельзя разрешать браузеру менять свой план на Pro.

## Перед запуском для клиентов
Нужны: политика конфиденциальности, удаление аккаунта и данных, экспорт/восстановление, проверка RLS и Storage policies, серверные резервные копии, ограничение запросов, тесты нескольких устройств и аудит безопасности. Не храните особо чувствительные данные учеников в прототипе.

## v6: тарифы, права доступа и серверная основа платежей
1. Сначала выполните `schema.sql`, затем `migrations/002_billing_entitlements.sql` в Supabase SQL Editor.
2. Интерфейс теперь получает тариф и флаги функций через RPC `tutor_my_entitlements()`. Браузер не может менять план: обновление подписки разрешено только доверенному серверному событию.
3. `supabase/functions/create-checkout-session/index.ts` проверяет сессию пользователя и разрешённый ID тарифа (`pro_monthly` / `pro_yearly`). Цена не принимается от браузера. Функция обращается к серверному адаптеру, который задаётся секретами `BILLING_ADAPTER_URL` и `BILLING_ADAPTER_SECRET`.
4. `supabase/functions/billing-webhook/index.ts` принимает только нормализованные события, подписанные HMAC SHA-256 в заголовке `x-tutor-signature`. События применяются через `tutor_apply_billing_event`; повторная доставка одного `provider + event_id` идемпотентна.
5. В Edge Functions нужно настроить секреты `APP_ORIGIN`, `BILLING_ADAPTER_URL`, `BILLING_ADAPTER_SECRET`, `BILLING_SUCCESS_URL`, `BILLING_CANCEL_URL`, `TUTOR_BILLING_WEBHOOK_SECRET`. For the checkout function, deploy with JWT verification enabled; the webhook function uses its HMAC check and has gateway JWT verification disabled in `supabase/config.toml`. Supabase автоматически предоставляет `SUPABASE_URL`; для webhook также нужен `SUPABASE_SERVICE_ROLE_KEY` в серверном окружении.

**Важно:** это provider-neutral каркас, не подключённый платёжный продукт. Для реального приёма платежей требуется реализовать адаптер под выбранного провайдера, проверку его нативной подписи, обработку событий оплаты/продления/возврата и тесты. Адаптер должен преобразовать событие провайдера в канонический JSON для `billing-webhook`, а затем подписать точные байты отправляемого тела секретом `TUTOR_BILLING_WEBHOOK_SECRET`. Не направляйте нативные webhook-события провайдера напрямую на эту функцию без адаптера и проверки подписи провайдера.

Права доступа в `tutor_my_entitlements()` пока являются серверным источником прав для интерфейса. Чтобы коммерчески ограничить функции, нужно применять эти права на каждом защищаемом серверном endpoint и в политиках данных; одного скрытия кнопок в браузере недостаточно.


### Деплой Edge Functions (после выбора и реализации провайдера)
В каталоге проекта, с установленным Supabase CLI и привязанным проектом:

```bash
supabase functions deploy create-checkout-session
supabase functions deploy billing-webhook --no-verify-jwt
supabase secrets set APP_ORIGIN=https://your-app.example
supabase secrets set BILLING_ADAPTER_URL=https://your-billing-adapter.example/checkout
supabase secrets set BILLING_ADAPTER_SECRET=replace-with-a-long-random-secret
supabase secrets set BILLING_SUCCESS_URL=https://your-app.example/?billing=success
supabase secrets set BILLING_CANCEL_URL=https://your-app.example/?billing=cancel
supabase secrets set TUTOR_BILLING_WEBHOOK_SECRET=replace-with-a-different-long-random-secret
```

Замените адреса и секреты на реальные значения. Не коммитьте секреты в Git и не вставляйте их в браузер. `BILLING_ADAPTER_URL` должен вести на ваш серверный адаптер, который интегрирован с выбранным платёжным провайдером. До его реализации оформление должно возвращать ошибку `billing_not_configured`, а не имитировать успешную оплату.


## v7: прямой Paddle Billing
Выполните `cloud/migrations/003_paddle_billing.sql` после `002_billing_entitlements.sql`, затем следуйте `cloud/PADDLE_SETUP.md`. Интеграция использует sandbox по умолчанию; серверные секреты и Paddle price IDs должны храниться только в Supabase secrets. Подпись webhook проверяется напрямую по алгоритму Paddle. Реальные платежи не будут работать, пока не настроены одобренный Paddle-аккаунт, цены, домен Checkout и notification destination.
